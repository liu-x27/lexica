# Lexica · Windows 离线英语词典

一个完全离线的桌面英语词典。数据只下载一次，之后不再联网。

- **340 万条词条**，其中 136 万单词、204 万短语搭配
- **按词性分组的义项**：中文释义 + WordNet 英文释义 + 语义域标注，义项多的词自动折叠并提供词性导航
- **权威例句**：WordNet 官方例句 + Tatoeba 英汉对照例句，例句按词性归到对应分组下
- **词源与古典引文**：GCIDE（韦氏 1913）的词根来源与 19 世纪文学用例
- **词形变化**：复数 / 过去式 / 过去分词 / 现在分词 / 三单 / 比较级 / 最高级 / 原形
- **难度范畴**：中考、高考、四级、六级、考研、雅思、托福、GRE、牛津 3000、柯林斯星级
- **词频**：COCA 当代语料库与 BNC 英国国家语料库双排名
- **词汇网络**：同义词、反义词、上位词、下位词，可点击跳转
- **按考纲练习**：14 个范围（中考到 GRE、常用词表、柯林斯星级）可学习、自测、水平检测
- **8 种题型**：选释义 / 选单词 / 例句填空 / 选同义词 / 听音选词 / 易混词辨析 / 看中文拼写 / 听音拼写
- **易混词辨析**：affect/effect、principal/principle 这类拼写近似但意思不同的词，词条页直接对照
- **自定义词表与词条**：粘贴一份单词表就能当练习范围；词库没收的新词可以自己补
- **实时字幕**：上课边听边出双语字幕并写进文件（麦克风 / 系统声音 / 导入录音），完全离线
- **视频字幕悬浮窗**：看电影/视频时抓系统声音，置顶半透明面板显示双语字幕，可鼠标穿透
- **划词取词**：选中其它程序里的文字直接查，走 Windows UI Automation 读选区（不碰剪贴板）
- 全局热键悬浮查词、剪贴板取词、拼写纠错、中文反查、生词本 + SM-2 间隔重复、离线发音朗读
- 每日目标、学习热力图、正确率曲线、学习数据一键备份恢复
- 两套完整主题：纸质浅色 / 玻璃深色，正文字号可调

技术上**不含任何需要编译的原生模块** —— SQLite 直接用 Node 内置的 `node:sqlite`
（FTS5、trigram 分词器、自定义函数都已验证可用），所以在没有 MSVC 构建工具的机器上也能装。

## 快速开始

```bash
npm install
```

```bash
npm run data
```

`npm run data` = `npm run fetch`（下载约 800 MB 原始数据，其中两个中文维基 dump 占 541 MB）+ `npm run build:db`（合并成 `data/dict.db`）。
国内网络下 GitHub 直连很慢，下载脚本会自动按顺序尝试 `gh-proxy.com` → `ghfast.top` →
`ghproxy.net` → GitHub 直连 → 系统代理，并支持断点续传。
走镜像下载完成后，脚本会回 GitHub 原站抽取头/中/尾三段做字节比对，确认镜像没有替换文件内容。

```bash
npm start
```

## 打包免安装版

```bash
npm run pack
```

产出 `dist/Lexica-win-x64/`，双击 `Lexica.exe` 运行，无需安装。

## 查词的解析顺序

1. 精确匹配词头
2. 词形还原：`running` → `run`（`forms` 表，来自 ECDICT `exchange` 字段）
3. 归一化重试：去连字符、空格互换
4. 拼写纠错：soundex 音近 + 等长邻域 + trigram 子串三路取候选，
   再用 Damerau-Levenshtein 距离重排（相邻字母调换算一次编辑，
   所以 `recieve` → `receive` 距离为 1）

中文输入会走另一条路，三级候选：

1. **精确义项片段** —— 查询词恰好是某个独立义项。查「高铁」时 `hi-rail` 的释义就是「高铁」，
   这是相关性最高的情况，走 `zh_seg` 表的索引，等值查找
2. **前缀片段** —— 以查询词开头的义项
3. **FTS5 子串** —— 出现在义项中间的（「高铁血红蛋白」这类），相关性最低

三路结果合并后按「查询词占命中片段的比例」统一重排。这个覆盖率必须是主排序键：
只按词频排，`ferric`、`hematin`、`siderocyte`（高铁**红细胞**）这些有词频记录的化学词
会把真正的答案压下去。

第 3 步的 bm25 排序在单字查询上很贵（「的」命中 42 万条，排序要 460ms），
所以只在查询至少两字、且前两级凑不够结果时才走——单字查询靠前两级索引，几十毫秒。

多词英文输入（如 `lasting a very short time`）走英文释义全文检索。

**整句输入**（六个词以上，或四个词以上带句读）走另一条路：`status: 'sentence'`，
返回句中术语 + 逐句翻译，见下面的「长句翻译」。这条分支加在词条/词形/维基术语
都没命中之后，所以 `gradient descent` 这类已收录的词组不会被抢走；
同时它照样附上拆词与全文检索结果——句子和长词组的界限本来就模糊
（`natural language processing toolkit for python` 六个词，算哪种都说得通），
两边信息都给出来，判偏了也不损失什么。

短语（204 万条，占词库六成）在两个方向都能查：英文方向直接命中词条，
中文方向也在索引里——`期望` 能查到 `look forward to`，`子弹头列车` 能查到 `bullet train`。

排序上有一层「权威性」概念：`words.weak` 标记那些没有任何权威信号的条目（无词频、无柯林斯、
无考纲标签、WordNet 也未收录）。ECDICT 从网络语料聚合而来，收了大量常见错拼
（`recieve`、`wierd` 都是正式词条）和纯变形条目（`ran`、`mice`）。因此：

- 搜索建议与检索结果里权威条目排前面，弱条目不作为「精确匹配」置顶
- 拼写纠错的候选池只收权威词，不会把错拼推荐给用户
- 查到弱条目时照常展示，但同时给出「可能是拼写有误」的纠正提示

## 例句的词性与义项归属

Tatoeba 例句不只是堆在词条底部，会尽量归到对应的词性分组甚至具体义项下：

- **词性归属**（约 50% 的关联）：看词头前一个词判断它在句中的语法角色。
  `win the game` 前面是 `the` ⇒ 名词，`has run down` 前面是 `has` ⇒ 动词。
- **义项归属**（约 0.6%）：比对例句实词与义项签名（同义词 + 上位词 + 释义实词）的重叠度，
  要求两个独立信号且明显胜过次优才绑定。

义项级别的召回很低，这是词汇重叠法的固有上限——Tatoeba 句子朴素，WordNet 释义抽象，
两者常常没有共同词汇。这里**刻意选择了高准确率而非高覆盖率**：绑错义项比不绑更糟。
签名里必须剔除词头自身及其所有词形，否则 WordNet 同义词集本就包含词头
（`run` 有个义项的同义词是 `flee; take to one's heels; cut and run`），
会让该义项对每条例句都拿满分。

## 按考纲练习

选一个范围（中考 / 高考 / 四六级 / 考研 / 雅思 / 托福 / GRE / 最常用 1000·3000·5000 词 /
牛津 3000 / 柯林斯 4·5 星），有三种用法：

- **学习浏览** —— 一张张过词，标「认识 / 不认识」，标为不认识的自动进生词本
- **自测** —— 四选一，10 或 25 题，答完即时反馈。五种题型可筛选：
  选释义、选单词、例句填空、选同义词、听音选词
- **水平检测** —— 按词频分高/中/低三层等量抽样 30 题，估算这个范围的掌握率，
  给出 95% 置信区间与分层结果
- **强化错题** —— 拿错得最多的词重新出题

题目全部从本地词库现算，没有预置题库。干扰项取自同范围、词频相近的词，
并排除正确答案的同义词——否则会出现两个都对的选项。

## 学术词组

读论文划词组时，词库常常没有整条。这里分三层解决：

1. **维基跨语言术语库（91.8 万条）** —— 中文维基条目标题的中英对照，人工校准，
   正好覆盖 `cross-validation → 交叉验证`、`zero-shot learning → 零样本学习` 这类学术术语。
   构建时会剥掉标题的括号限定（`Cross-validation (statistics)` 也要能用 `cross-validation` 查到），
   并用 OpenCC 转成简体——中文维基约一半标题是繁体。
2. **逐词拆解** —— 整体查不到时把词组拆开，逐个给释义（含词形还原：`embedding → embed`），
   再列出词库里的相关搭配。读论文时往往只有一个词是障碍，拆开就够用。
3. **机器翻译（可选，手动触发）** —— 见下。

「有没有维基条目」还顺带解决了一个排序问题：词组结构上不可能有词频、柯林斯、
WordNet 记录，所以之前只能按词长排，结果输 `gradient` 推的是 `gradient gun`
而不是 `gradient descent`。维基条目的有无是目前唯一能区分真实术语与生僻组合的信号。

## 机器翻译兜底（可选）

```bash
npm run fetch:model
```

下载 opus-mt-en-zh 量化模型（整个目录 118 MB，其中两个 onnx 权重 108 MB），用 onnxruntime-node 原生推理，全程离线。

词典给不出整体释义时**自动触发**（设置里可关）。结果排在逐词拆解之后，
用虚线框和「机器翻译 · 仅供参考」标签与人工释义区分——顺序很重要，下面的实测数据说明了原因。

模型跑在独立的 `utilityProcess` 里，**不能放主进程**：ONNX 的加载与推理会长时间占住线程，
放主进程会把 IPC 和窗口绘制一起卡死，实测连 `capturePage` 都会超时。
启动 2 秒后后台预热，第一次划词不用等那 108 MB 权重现加载。

实测质量（`npm run eval:mt` 可复现）：

| 输入 | 模型输出 | 正确译法 |
|---|---|---|
| ablation study | 通货膨胀研究 | 消融实验 |
| overfitting | 超装 | 过拟合 |
| gradient descent | 梯度 下位 | 梯度下降 |
| to the best of our knowledge | 尽我们所知 | ✓ 可用 |
| we hypothesize that | 我们假设 | ✓ 正确 |

**术语上它错得很自信**（把 ablation 当成了 inflation），比查不到更有害；
但自由表达和整句译得不错，而那恰好是词典本来就覆盖不了的部分。
所以只在词典与术语库都没有结果时给一个明确标注的按钮，由用户决定要不要看，
结果用虚线框与「机器翻译」标签和人工释义区分开。单次约 250ms，首次加载约 1.8s。

## 长句翻译

三个入口，都走同一套渲染：

1. **查词框**输入或粘贴整句 —— 直接出结果页
2. **侧栏「翻译」页** —— 多行输入可粘整段，`Ctrl+Enter` 开始，逐句显示进度
3. **划词浮窗** —— 在别的程序里划一整句，浮窗直接给译文

结果分两段：**句中术语**在前，**双语逐句对照**在后。

### 为什么必须双语对照

整段实测下来，这个模型在学术文本上的问题不只是「术语不准」：

| 原文 | 模型输出 |
|---|---|
| We release **code and checkpoints** to facilitate **reproduction**. | 我们发布**密码和检查站** 方便**生殖** |
| performance scales **log-linearly** | 性能尺度的**日志比例** |
| degrades accuracy from 71.2 to **63.8** | 将直线概率从 71.2 降低至 **638** |

最后一行的小数点被吃掉了——**这是数字被改错**，不是语句不通顺。
所以界面上**没有「只看译文」的版式**：永远逐句并排原文与译文（窄屏改上下排 + 竖线），
让这类错误一眼可见。可靠信息（词库术语）排在译文之前。

### 句中术语

用 n-gram（4 词到 1 词）查词库，长术语优先，命中后占位避免重复。三条降噪规则都是照实测定的：

- **多词术语必须 `wiki=1`**。不加这条，ECDICT 收的 `a form of`、`form of`
  这类功能词组合会把列表淹掉
- **单词先做词形还原再判罕见度**。`improving` 自己有词条（释义是「有启发的」），
  不还原就会冒出既噪音又误导的结果
- **只留罕见词**（bnc/frq 在 4000 名以后）。常用词不需要在这里重复解释

科学类句子效果很好（`adenosine triphosphate → 三磷酸腺苷`、`oxidative phosphorylation → 氧化磷酸化`），
但覆盖有限：2019 年后的术语大量缺失（`large language model`、`in-context learning`、
`ablation study` 都查不到），且有几个命中了却是错义（`transformer → 变压器`、`dropout → 退学学生`）。
要补得刷新 zhwiki 转储。

### 切句

模型一次只吃得下 512 token，整段塞进去会被静默截断，所以按句切开逐句翻，
译完一句立刻回报进度。缩写后面的点不算句子边界（`et al.`、`e.g.`、`J. Doe` 都有测试），
但**只有「整段就是一个编号」才当列表标记挡住**——不能一见数字结尾就挡，
`improved to 0.91.` 和 `in Tab. 2.` 都是正常句尾。换行是硬边界。

工作进程里的请求**必须串行**：`parentPort.on('message', async …)` 不等上一条处理完
就派发下一条，多个请求并发调用同一个 pipeline 会慢到 8 秒都出不来结果。

### 想换模型

`node scripts/eval-mt-candidates.mjs --probe` 列出候选与下载量，

### 为什么用 whisper.cpp 的预编译 exe

先试了 transformers.js 的 ONNX Whisper（和翻译模型同一套栈），**跑不动**：

| 分段长度 | transformers.js (base.en) | whisper.cpp (base.en-q5_1) |
|---|---|---|
| 5s | 0.58x（跟不上） | **4.00x** |
| 10s | 1.04x（跟不上） | 3.42x |
| 30s | 1.88x | 1.88x（无需） |

ONNX 那条路必须把分段拉到 20-30 秒才跑得动，上课延迟半分钟没法用。
whisper.cpp 在 5 秒分段上是 4 倍实时余量。它是独立 exe 而不是 Node 原生模块
（本机没有 MSVC 编不了），当子进程用——项目里已有先例（划词的 PowerShell 助手）。

### 三个决定性的实现细节

**`--audio-ctx` 是这个功能能不能用的关键。** whisper 的编码器窗口固定 30 秒，
短音频也按满窗算。缩小它把 5 秒分段从 1.50x 提到 4.00x，**文本逐字相同**。
但它不能随便设小：实测 `ac=512` 只覆盖约 10.5 秒，喂 14 秒音频时不是丢尾巴，
而是**退化成重复循环**（反复吐同一句）。所以 `ac` 由分段上限按「约 49 帧/秒」推出来，
两个参数在代码里绑死（`LECTURE_MAX_CHUNK_SEC`）。

**分段必须按静音切，不能按固定时长。** 固定 5 秒切会把句子剖开：
`...receives a scalar reward.` / `signal at each time step.` ——两个错句。
`vad-chunker.js` 按句间停顿切，门限自适应（用最近 8 秒帧能量的低分位数估噪声地板）。
但「丢不丢这一段」不能依赖那个门限——窗口里全是语音时它会退化到高过语音，
所以另有一个绝对能量兜底，否则会把整段讲话当静音扔掉。

**whisper 的内部分段要合回一条。** 它会把一个音频块再按自己的规则切成几段，
不合的话一句话会被劈成两条字幕，而且喂给翻译的是残句——实测
`...fundamentals of reinforcement` / `learning.` 分开后前半句译成了「加强部队的基本内容」。
句子边界由 VAD 决定，whisper 的内部切分是artifact。

### 识别质量：三个可调项的实测

同一段 127 词的音频，按 WER（词错误率）打分（`scratchpad/asr-quality.mjs`）：

| 配置 | WER | 最慢段 | 实时倍率 |
|---|---|---|---|
| base 贪心 | 4.7% | 314ms | 19.3x |
| base + beam5 | **6.3%** | 564ms | 11.4x |
| base + 领域提示词 | 3.1% | 648ms | 13.3x |
| small 贪心 | 4.7% | 1289ms | 5.1x |
| small + 提示词 | 1.6% | 1628ms | 3.8x |
| **small + beam5 + 提示词（默认）** | **0.8%** | 1702ms | **3.7x** |

三条结论：

1. **`small` 能跑实时。** 早先「small 只有 0.62x」是拿 whisper-cli 每段重载模型、
   且没有 audio-ctx 时测的，那个结论是错的。常驻服务 + audio-ctx 之后它有 3.7 倍余量。
2. **领域提示词是单项收益最大的。** whisper 把它当已转写的上文，于是更倾向于输出
   里面出现过的写法——能把 `twinning` 这种同音错词拉回 `training`。
   课程名会自动拼进去，术语在设置页里填。
3. **beam search 不能一刀切。** 它让 small 从 1.6% 降到 0.8%，但让 base 从 4.7%
   涨到 6.3%——小模型的候选序列本来就不可靠，扩大搜索更容易选到错的。
   所以 beam 是按模型档位配的，不是全局设置。

（这是 TTS 合成音频，比真实教室干净，绝对数字会更高，但相对排序可信。）

### 翻译质量：为什么没做「用词库自动修正术语」

看起来很自然的想法：译文里的术语用词库的译名替换掉。实测不可行——
词库对课堂词汇的命中是 8/15，而错的那些会**主动引入错义**：

| 术语 | 词库给的 | |
|---|---|---|
| reinforcement learning | 强化学习 | ✓ |
| gradient descent | 梯度下降 | ✓ |
| value function | **明度函数** | 光学义 |
| scalar | 数量, 纯量 | 不是标量 |
| replay buffer / temporal difference / actor critic / ablation study | **没收录** | |

更糟的是从整句抽取时 `replay buffer` 抽不到，只抽到 `replay → 重新比赛, 重演`。
自动替换会让译文更差。可靠的路是**用户自己的术语表**（发现译错了加一条，以后都对），
见下面的「术语表」一节。

### 实时场景下翻译模型要用快的

识别和翻译是两个独立进程，本该流水线重叠。但实测 **NLLB 会和 whisper 抢 CPU**，
两边一起变慢——一节课的字幕只识别出四分之一，识别队列 25 秒都排不完。
所以：翻译进程的 ONNX 线程数限制到 4，且实时字幕单独用一项设置
（`lectureMtModel`，默认 opus），查词与翻译页仍用 `mtModel`（默认 NLLB）。
转写文件里留着英文原文，课后想要更准的译文可以在翻译页重译。

### 崩溃安全

一节课一个多小时，中途崩了不能全丢。所以**无论选了哪几种导出格式，总是写一份
`journal.jsonl` 流水账**（同步追加，不用 WriteStream——流的缓冲会让刚写的内容没落盘，
断电就丢，而这正是流水账要防的事）。md/txt/srt 是追加式生成的，json 在结束时汇总。
上次没正常结束的话，历史列表里会标出来，点「恢复」即可从流水账重建全部成品。

另一个约束是**译文比原文晚到**：识别出英文后才送去翻译，两者差一两秒。
所以维护一个按时间排序的待写队列，只有队首那条齐了才推进游标，
翻译失败的条目也要放行——否则后面全堵住。

### 准确度

识别和翻译各有各的错法，两边都会出错：

| 实际 | 识别成 | 译成 |
|---|---|---|
| training | **twinning** | — |
| non-stationary | **numb** / stationary（句中停顿被当成句边界） | — |
| reinforcement learning | ✓ | **加强学习**（应为强化学习） |
| policy | ✓ | **政策**（应为策略） |
| value function | ✓ | **价值功能**（应为价值函数） |

所以界面**始终英中对照**，没有「只看中文」的排版；数字、公式、人名请以英文原文为准。

## 视频字幕悬浮窗

看电影、看视频时抓系统声音，在一块置顶的半透明面板上显示双语字幕，像播放器自带字幕。

- 默认热键 `Ctrl+Alt+S`，托盘菜单里也有
- 拖动、调字号、显示条数（1~4 条）都在窗口上
- **锁定**后鼠标穿过字幕能点到后面的播放器；此时窗口自己点不到了，只能靠热键关
- 不生成成品文件（看电影不需要留记录），但流水账照样写——
  看到值得记的内容可以去「实时字幕 → 历史」里点「恢复」

实现上与课堂字幕共用同一条流水线（识别 + 翻译），只是 `formats` 传空。
两个差别：

- **采音放在悬浮窗自己的渲染进程里**，不放主窗口。看电影时主窗口会被最小化或挡住，
  而 Chromium 会限流不可见窗口的定时器——这个坑在做课堂自测时踩过，卡了 19 分钟。
  悬浮窗是置顶常显的，采音链在这里最稳。
- **不传领域提示词**。影视对白不是学术演讲，学术术语提示词只会把它往术语上带偏。

窗口不能「失焦即隐藏」（悬浮查词窗是那样的）：看电影时焦点一定在播放器上，
那样会刚打开就消失。

## 生词本：自己的释义与笔记

每个生词都能写**我的释义**和**我的笔记**，写完会出现在列表、词条页和复习卡上。
入口三个：生词本行内的引号图标、词条页标题栏的引号图标、生词本顶部的「手动添加」。

**注释是叠加，不是替换。** 词库里有这个词时，词条页照常显示词库释义，
「我的」单独一块排在最前面；词库里没有（自己加的词组）时，我的释义就是它唯一的释义。

### 为什么不复用「自定义词条」

`custom_entries` 那张表的语义是**整条替换**词库条目（查词时优先它，另给一个链接
回到内置词条），而且和生词本完全脱节——在生词本里看不到、复习时也带不出来。
注释挂在 `wordbook` 行上：删词时一起走，语义干净。

### 词库里没有的词组，原来是死路

读论文划到的词组多半查不到整体，而「没有找到」页和「逐词拆解」页
**都没有收藏按钮**——想收进来一点办法也没有。现在两个页面底部都有
「加进生词本，自己写释义」，点进去直接是填好词的编辑框。

顺带补了一个一直空着的坑：`wordbook.note` 这一列从 v1 建库起就存在，
但**从来没有任何代码写过它或读过它**，笔记功能等于不存在。

### 三处容易踩的实现细节

- **`addWord` 不能用 `toggle`。** toggle 对已存在的词是**删除**，
  拿它来存编辑框会让「保存」变成「删除」。同理「移出生词本」要用 `remove`，
  用 toggle 的话连点两下会把刚删的词又加回来（两条都有测试盯着）。
- **列表是虚拟滚动，行高锁死 76px**（`WB_ROW_H`），塞不进第三行。
  所以笔记接在释义后面、同一行、颜色更淡、超出省略，全文在编辑框里看。
- **重绘会冲掉正在输入的内容。** 表单上带 `data-for` 记着它是给哪个词渲染的，
  回收草稿时必须比对——从别的页面点「编辑另一个词」进来时，生词本视图里
  还挂着上一个词的旧表单，不比对就会把旧词的输入写进新词的草稿。

导出 CSV 多了「我的释义」「我的笔记」两列。Anki 那边列数固定，
自己写的内容拼进背面（多加列会让导入时字段错位）。

### 顺手补了 shot 流程的两个诊断盲点

做这个功能时被这两点各绕了一轮，都不是产品 bug 而是**验证工具骗人**：

- **渲染层抛的异常原本完全不可见。** 界面只是「没有变化」，日志里一行都没有，
  截图看起来像断言写错了。现在 `console-message` 转发到主进程日志。
- **开头那句 `await wait(1600)` 不够。** 词库 1.2 GB，文件不在系统缓存里时
  （连着跑几个 Electron 实例就会把缓存挤掉）加载更慢，第一次查词会静默落空：
  `go()` 见 `state.stats.ready` 为假直接 return，界面停在首页，然后
  「#stage 不是滚动容器」那条布局断言跟着误报——**看着像布局坏了，
  其实是词库还没加载完**。改成轮询 `window.__lexicaShot.ready()`。
  断言里也把 `sections` / `head` 打出来，好分清「布局坏了」和「压根没渲染」。

## 字幕为什么慢，以及怎么治

先量再改。给流水线加了分段计时（日志里的 `[lat]`），真实语音跑 13 段：

| 环节 | 实测 | 占比 |
|---|---|---|
| 等说话人把话说完（音频块本身长度） | 3.2–7.7s，中位 **4.8s** | ~80% |
| 排队 | **0ms**（完全不积压） | 0% |
| 识别（small + beam5） | 750–1006ms，中位 920ms | ~15% |
| 翻译（opus） | 134–987ms，中位 **300ms** | **~5%** |

**「字幕慢」几乎全部来自等停顿，翻译只占 5%。** 换在线翻译服务改善不了这件事——
这是动手前必须知道的，否则会去优化错的东西。吞吐量（3.7 倍实时）和延迟是两回事：
前者说的是「处理得比说得快」，后者才是「字幕落后多少」。

### 滚动字幕：治延迟的那一项

正式字幕要等 VAD 切段（420ms 静音，或攒到 9 秒强切）。滚动字幕拿「说到一半」的
音频先识别一遍，边说边推临时稿，说完再被定稿替换。

![滚动字幕：斜体的临时稿随后被准确的一遍替换；定稿里术语表修正了术语](docs/screenshots/captions.gif)

自测的录屏。标着 `···` 的斜体行是临时稿——`Over many episodes it learned.`——几帧之后
被准确那一遍的整句替换。它没有中文，因为临时稿只走在线翻译，而在线默认关着。
定稿里能看到术语表在起作用：带着为这节课准备的 8 条术语，译文是「强化学习」
「智能体观察了状态」「经验回放缓冲」；不带术语表时，同一段音频出来的是「加强学习」
「特工观察了国家」「重播缓冲」。剩下两句（`Takes in action`、`NYOFF`）错在识别阶段，
术语表够不到。

合成人声，自测按 4 倍速喂入，每 450ms 截一帧——所以这里看的是流程，不是实时的节奏；
延迟以上面那张表为准。

`VadChunker.peek()` 返回当前攒着还没切出去的音频，**不消耗**它。两个坑：

- **必须返回拷贝。** 这份 buffer 要经 IPC 传走，结构化克隆会把它 detach，
  给 subarray 的话还没切出去的音频会凭空消失（`_take` 那里踩过同一个坑）。
- **必须看 `sawSpeech`。** whisper 对纯静音会凭空编出句子来。

三条纪律，写在代码里也写在这儿：

1. **临时稿绝不落盘。** 每 1.5 秒出一版半句，漏进转写稿就是几百条残句，
   而且文件看起来是满的、不容易发现。自测里有一条断言：journal 的 seg 行数
   必须等于定稿数。
2. **正式字幕优先。** 有正式活儿在跑就跳过这一次临时稿。
3. **过期的丢掉，不排队。** 临时稿的价值只在「现在」。

**临时稿用单独一个识别服务**（小模型、限死 4 线程；本机 24 核，主服务占 12）。
不复用主服务的原因：请求在服务端是串行的，一次临时稿（small+beam5 约 900ms）
会把正式字幕往后推同样长的时间，正好抵消掉想省的延迟。临时稿反正会被覆盖，
准不准无所谓，快才重要。

**节奏由音频回调驱动，不能用 `setTimeout`。** Chromium 会把不可见/被遮挡窗口的
定时器限流到每秒一次甚至更慢——而滚动字幕最需要它的场景恰好是「主窗口被播放器遮住」。

**临时稿和定稿必须共用同一个渲染函数。** 第一版我给临时稿单独拼了一份 DOM，
结果漏掉了 `.lec-texts` 那层包裹——`.lec-row` 是 `52px + 1fr` 的两列网格，
英文于是掉进 52 像素宽的时间列里，一行只排得下一两个词、竖着拖出半屏。
复制一份结构就会立刻漂，所以 `Lx.lectureRow(seg)` 多接一个 `seg.partial`，
两边都走它。自测里加了一条断言：临时稿的正文列宽不得小于定稿的 90%。

### 在线翻译：治质量的那一项

默认关，设置页里开。开了之后要翻译的英文会发给该服务（上课时就是老师讲的内容），
界面上写明了这点。

**速度上两边差不多**，在线的波动取决于连接热不热。应用内跑了三轮实测：

| | 次数 | 中位 | 区间 |
|---|---|---|---|
| 在线（Google） | 40 | **99ms** | 41–524ms |
| 本地 opus | 32 | 162ms | 72–1291ms |

有一次超时退回本地，那一条总共花了 2.3 秒。不过这些都不太要紧——
翻译本来就只占延迟的 5%，而且**英文行是在发起翻译之前就推出去的**，
翻译慢或失败只会让中文晚到。

本地模型的问题不是「不通顺」，是**改错内容**：

| 原文 | 本地 opus | Google |
|---|---|---|
| degrades accuracy from 71.2 to **63.8** | 从 71.2 降低至 **638** | 从 71.2 降低到 **63.8** ✓ |
| **code and checkpoints** … **reproduction** | **密码和检查站** … **生殖** | **代码和检查点** … **复制** ✓ |
| a **scalar** reward | 一笔**奖金**（术语消失） | **标量**奖励 ✓ |
| … estimate the **value function** | （整句被截断吞掉） | 估计**价值函数** ✓ |

「数字会被改错」原本就是界面强制双语对照的理由。

用的是 `translate_a/single?client=gtx`，也就是网页版翻译那个接口：不需要 key，
但**不是公开 API**——没有 SLA、随时可能改动，严格说也不在 Google 付费 API
的条款内。所以默认关、可随时切回本地、**任何失败都自动退回本地模型**。

**一条排查记录，因为我先判断错了。** 接进来之后稳定收到 HTTP 429，我写下了
「这个端点会限流」。其实是请求通道选错了：同一时刻、同一个 URL，Electron 主进程的
全局 `fetch` 给 429，而 `net.fetch` 和 `node:https` 都是 200。必须把 `net.fetch`
显式传进去。这个错误能瞒过去还有第二个原因——自测断言当时只看译文文本，
429 降级到本地、而本地那句恰好也译对了，断言照样打勾。现在断言查的是
`via === 'online'`，也就是**这次请求到底走的哪条通道**。

四条实现要点：

- **实时字幕的超时只给 1.2 秒。** 字幕的价值随时间衰减，宁可退回本地拿一句差一点的，
  也不能让字幕停着等网络。整段翻译给 8 秒。
- **连续失败 3 次进冷却一分钟。** 断网时如果每句都去等一次超时，字幕会被拖慢而不是
  退回本地——那比不开在线更糟。
- **批量用换行分隔。** 实测换行原样保留、顺序不变，4 句一次往返 531ms。但**不能盲信
  1:1**：服务端可能合并或拆分行，行数对不上就退回逐句，否则译文和原文错位。
- **术语表探测要用不过术语表的原始通道。** 拿已经被术语表修正过的译文去探，
  探到的永远是用户自己写的译名，整个机制空转。换通道（本地↔在线）等于换模型，
  会自动作废探测缓存——不然术语表在新通道上一条都命中不了，而且是静默失效。

临时稿的译文只在**在线可用时**才给：本地模型一句 300ms 且和识别抢 CPU，
每 1.5 秒来一次会把正式字幕拖慢，用延迟换译文方向正好反了。

而且临时稿的译文**最多 2.5 秒给一次**。连续两版临时稿是「越来越长的前缀」，
缓存一次都命不中——一节 50 分钟的课就是约 2000 次请求。这是个免费的非官方端点，
没必要把请求量花在临时稿上：它几秒后就被覆盖，定稿的译文才是要写进文件的。

## 术语表

「自定义」页第三个 tab。写下你要的译名，实时字幕、视频字幕、整段翻译、划词浮窗
四条链路的译文都会跟着改。只在装了翻译模型时出现——它修的就是机器翻译的输出。

```
policy = 策略
value function: 价值函数
replay buffer    经验回放缓冲
```

分隔符用 `=` `:` `|` 逗号 制表符 或**两个以上**空格都行。单个空格不行——
多词术语本身就带空格，`replay buffer 经验回放缓冲` 无法判断边界，这种行直接跳过。

### 两个门槛

只在**两个条件同时成立**时才动译文：

1. 英文原文里确实出现了这个术语（整词匹配，`policy` 不命中 `policymaker`）；
2. 译文里确实出现了这个术语的某个**已知错译写法**。

缺一不可，这是整个功能的安全边界。只看条件 2 的话，「政策」这个词在任何谈政策的
句子里都会被改成「策略」；只看条件 1 的话，我们并不知道该换掉译文里的哪几个字。
自测里带一条反向对照：`The government announced a new economic measure.`
的译文含「政策」但英文里没有 `policy`，必须保持原样。

还有一条长度门槛：**单字错法不用来替换**。实测 `scalar` 探到的错法是「标」，
拿它去替换会把整句改烂。两个字以上是允许的——中文术语大多就两个字。

### 错译写法从哪来

替换的前提是知道该换掉译文里的哪几个字，这个只有模型自己知道，所以要问它一次，
结果存进 `glossary.wrong`（JSON 数组）。加术语时在后台问，不阻塞字幕。

**怎么问很关键。最初的做法（把术语单独喂给模型）是最差的一种**：

| 问法 | `replay buffer` 得到 | 对得上真实句子 |
|---|---|---|
| A 裸术语 | 重放缓冲 | 2/8 |
| B 带冠词 `the X` | 重放缓冲 | 2/8 |
| C 框架句做差 `We use the X.` 减 `We use the thing.` | 重播缓冲 | **5/8** |
| 三者并集 | | **6/8** |

原因是**模型对同一个术语的错译不是固定的**，取决于上下文：`replay buffer`
单独问给「复制缓冲器」，而在 `We train the policy with a replay buffer…` 里
出现的是「反弹缓冲」，两者对不上，替换就不会发生。所以三种问法全用、取并集。

三个细节都是实测踩出来的：

- 模型拿到孤零零一个词时会**原地打转**——`policy → 政策政策`、
  `baseline → 基准基准基准基准`、`scalar → 标标`。不折叠这些重复，
  探到的写法在真实译文里永远匹配不上，等于白问一次（A 那一栏因此从 1/8 变成 2/8）。
- 框架做差会把**框架自己的词吸进来**：`value function` 的差异段是「使用价值函数」。
  这种写法一旦命中，替换会连「使用」一起删掉。所以差异段含有对照译文里的字就作废。
- 探到的写法常常**比译文里实际出现的多一个尾字**：`replay buffer` 探到
  「反弹缓冲器」，句子里是「反弹缓冲」，差一个「器」这条术语就白配置了。
  所以匹配时也试一次「去掉最后一个字」的形式——**只削一个，且削完必须还剩三个字**。
  放宽会出事：「反弹缓冲器」一路削成「反弹」，那两个字在别的句子里也会出现。

剩下对不上的两条里，`scalar` 那条**根本修不了**：`a scalar reward` 被整段
译成「一笔奖金」，术语在译文里压根没出现，任何替换都无从下手。

`scripts/probe-glossary-carriers.js` 是这组数据的来源（跑 Electron，不是 node）。

### 换了翻译模型要重新探测

`opus` 和 `nllb` 错得不一样。术语表里有「重新探测」按钮，新探到的写法**并入**
而不是覆盖旧的——反正还有「英文原文里必须出现这个术语」那道门槛，多存不危险。

记录进行中不做后台探测：探测本身要跑模型，而翻译进程和 whisper 会抢 CPU
（见上面「实时场景下翻译模型要用快的」）。上课时插进来几十次额外推理，代价是丢字幕。

每条术语右边的数字是**实际修正次数**。数小不代表没用：只有模型译错时才会计数。

## 划词取词

选中其它程序里的文字直接查。设置页有三档：关闭 / 按热键取词 / 划完自动弹。

本机装不了原生模块，所以由一个**常驻的 PowerShell 辅助进程**（`src/main/selection-helper.ps1`）
承担这件事——它能加载 .NET 的 UIAutomation，也能用 `Add-Type` 在运行时编译 C# 做 P/Invoke。
常驻是必须的：`powershell.exe` 冷启动实测 256ms，每次取词现拉一个根本没法用。

两条取词路径：

1. **UI Automation**（默认）—— 读焦点元素的 `TextPattern` 选区。不碰剪贴板、无副作用。
   浏览器、Office、WPF 与 Electron 程序支持较好；**老式 WinForms 程序通过 MSAA→UIA
   桥暴露出来只是个不支持任何模式的 Pane，读不到**。
2. **模拟 Ctrl+C**（可关）—— UIA 读不到时兜底。取词前把剪贴板各格式的**值**取出来备份，
   取完立刻还原。注意不能只留住 `GetDataObject()` 返回的那个 IDataObject：
   它是指向系统剪贴板的活引用，清空剪贴板后再拿去还原会失败，用户的剪贴板就丢了。

「划完自动弹」用 `GetAsyncKeyState` 轮询鼠标左键，不装全局钩子——`WH_MOUSE_LL`
的回调要在带消息循环的线程里跑，跨进程回调 JS 极易出问题，而 40ms 一次的轮询开销可以忽略。

几个实现上必须注意的点（都踩过）：

- 辅助脚本跑在 STA（剪贴板 API 要求），**必须泵消息**（`Application.DoEvents()`），
  否则 UIA 的跨进程 COM 调用完不成封送，`GetSelection()` 一直返回空
- `INPUT` 是联合体，大小由最大成员 `MOUSEINPUT` 决定（x64 上 40 字节）。只声明
  `KEYBDINPUT` 会让 `Marshal.SizeOf` 算成 32，`cbSize` 不对时 `SendInput` 直接返回 0
- `$pid` 是 PowerShell 的只读自动变量，不能拿来当局部变量名
- 含中文的 `.ps1` 必须存成 UTF-8 **BOM**，否则 PS 5.1 按 GBK 解码会把字符串引号拆断。
  `npm run check:bom` 会校验，`--fix` 可就地修复

## 数据库结构

| 表 | 内容 |
|---|---|
| `words` | 词头、音标、中英释义、词性占比、考纲标签、词频、柯林斯、词形变化原始串 |
| `forms` | 词形 → 原形 映射 |
| `senses` | WordNet 义项：词性、序号、英文释义、语义域、同反义、上下位、官方例句 |
| `sentences` / `word_sentences` | 例句库与词↔句关联（按质量分排序，句子文本只存一份；带 `pos` 词性归属与 `sense_id` 义项归属） |
| `etym` / `quotes` | GCIDE 的词源与古典引文（只取这两项，不引入其 1913 年的释义） |
| `word_tags` | 考纲/词表归属 + 是否够出题。`words.tag` 是空格分隔字符串，按 `LIKE '%toefl%'` 抽词要全表扫 340 万行（实测 282ms），拆表加索引后是毫秒级 |
| `zh_seg` | 中文释义切出的独立义项片段（441 万条，≤10 字）。让「查询词等于某个义项」变成索引等值查找，单字中文反查不必再走全量 bm25 排序 |
| `confusables` | 易混词对（3.8 万对）。在考纲词里按首字母 + 长度分桶后算编辑距离 ≤2，并剔除同义词与词形变化 |

用户数据（生词本、练习进度、自定义词表与词条、术语表、设置）单独存在 `%APPDATA%\lexica\user.db`，
用 `PRAGMA user_version` 做版本化迁移。**加迁移只能往数组末尾追加，不要改动历史项**——
老库里记着版本号，改历史迁移会让它走进不一致状态。设置页可以一键备份/恢复整个 user.db。
| `fts_en` | 词头 + 英文释义，porter 词干分词 |
| `fts_zh` | 中文释义逐字索引，支持任意长度中文反查 |
| `fts_tri` | 词头 trigram 索引，拼写纠错候选通道一 |
| `fuzzy` | soundex + 长度 + 词频，拼写纠错候选通道二 |
| `meta` | 构建时间与各项统计 |

用户数据（生词本、复习进度、设置）单独存在 `%APPDATA%\lexica\user.db`，与只读词库分离。
